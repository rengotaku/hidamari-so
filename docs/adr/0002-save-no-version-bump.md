# ADR 0002: 保存の版を上げず、欠けた項目は読み込み時に補う

## 背景

保存は localStorage の 1 件で、`schemaVersion` を持つ（`src/save/schema.ts`、現在 2）。版が違う保存は、移行関数があれば段階的に移し、無ければ捨てて新しいゲームにする（`src/save/migrate.ts` の `migrateSave`）。

版 2 の公開後に、次の機能が項目を足した。

- 町並みの変化 `town`（#9）
- 部屋の装飾・退去後の部屋・大家（#4）
- 時間の速さ `speed`（#14）
- 大家の所持金・出ていった住人・買収提案の状態（#5）

放置ゲームは、遊んでいる人の保存が長く残るのが価値なので、機能を足すたびに保存を捨てる、または移行関数を書き続けることを避けたかった。#14 の事前設計テスト S6 は「速さの項目が無い古い保存は 1 倍で始まり、保存が壊れない（v2 のまま読める）」を要求している。

## 決定

- 項目を足すだけなら `schemaVersion` は上げない。欠けた保存は読み込み時に補う。
  - 単純な既定値で済むもの: zod の `default` / `optional` で補う（`town` は `{}`、`landlordMoney` は 200000、`departed` は `[]`、`buyout` は `{ phase: "none", voice: null }`、`speed` は未指定なら 1）。
  - 種類ごとの計算が要るもの: `fillHouse`（`src/save/migrate.ts`）が、検証の前に補う。住人の `decorPlan` と `settled` を種類の装飾のセットから作り、`decor`（部屋ごと）、`vacancies`、`landlord` を埋める。乱数は使わず、同じ保存からは同じ結果になる。
- 欠けている項目だけを補い、あるものは触らない。壊れた値は補わず、検証で落とす（保存全体が読めなくなり、新しいゲームになる）。
- 版を上げるのは、既存の構造を置き換えるときだけ。そのときは `MIGRATIONS` に「版 N → N+1」の関数を 1 件足す（版 1 → 2 で日誌を文字列から構造に置き換えたのが唯一の例）。

## 捨てた案

- **項目を足すたびに版を上げ、移行関数を書く**: 移行関数が積み上がる。足しただけの変更は、既定値で補えば同じ結果になるので、関数を書く価値に見合わない。
- **版が違う保存は捨てる**: 遊んでいた町が消える。放置ゲームでは最も避けたい。

## 変えてよい前提 / 壊すと危ない前提

- **変えてよい**: 補う既定値（大家の所持金の初期値 200000 など）。ただし、すでに補われた保存の値は変わらない。
- **壊すと危ない**:
  - 足した項目は、欠けていても読める形（`default` / `optional`、または `fillHouse` の補完）で必ず足す。必須の項目として足すと、足す前の保存が検証で落ち、遊んでいた町が消える。
  - 補完は決定的であること（乱数を使わない）。`src/save/house.test.ts` の「補完は決定的」が見ている。
  - `SCHEMA_VERSION` を上げるときは、同時に `MIGRATIONS` へ移行関数を足す。足さないと、古い保存は `migrateSave` が `null` を返して新しいゲームになる。`src/ui/speed.test.tsx` の S6 と `src/save/house.test.ts` は、現在の版 2 のまま読めることを前提にしている。
  - 既存項目の意味や形を変えるとき（例: 配列の長さ、enum の値）は、足すだけではないので版を上げる側の判断になる。この境界を決める自動の検査はない（未確認）。
