# ADR 0003: 装飾は 2.5D の箱を正とし、全体図の平面はそこから導く

## 背景

部屋の装飾は、最初（#4）は全体図用の平面の矩形の並びでデータ化した。その後、部屋を押すと 2.5D で大写しになる機能（#8）が入り、同じ部品を奥行きのある形で描く必要が出た。全体図用と大写し用の 2 つの絵を別々に定義すると、部品を足すたびに二重に書くことになり、食い違う（親 #1 Decision Log #13）。

## 決定

- `content/decor.json` の部品は、`boxes` だけを持つ。1 つの箱は `[x, y, z, 幅, 奥行き, 高さ, 色]` で、`x` は左から、`y` は奥の壁から手前へ、`z` は床から上へ。
- 大写し（`src/render/closeup.ts`）は、この箱を立てて描く。
- 全体図（`src/render/decor.ts`）は、`src/content/decor25.ts` の `flatRects` が箱を正面から見た矩形 `[x, 上からの y, 幅, 高さ, 色]` に落としたものを、置き場所ごとの区画に並べて描く。上からの位置は `部品の高さ - z - 箱の高さ`。
- 奥にある箱から先に重ねる。同じ奥行きは定義の順（`orderedBoxes`）。大写しも全体図も同じ順で描く。
- 旧形式（平面の `rects` を持つ部品）は、スキーマが通さない（`src/content/decor25.test.ts`）。
- 装飾はキャラの種類と結びつけて抽選する（`archetypes.json` の `decor` に `required` / `pool` / `pick`）ので、部屋を見ればどんな人か分かる。

## 捨てた案

- **全体図と大写しで別々に絵を定義する**: 部品ごとに 2 回書く手間と、食い違いの元になる。
- **大写しの絵を平面から推測して立てる**: 奥行きと高さの情報が平面には無いので、良い見た目にならない。

## 変えてよい前提 / 壊すと危ない前提

- **変えてよい**: 部品の中身と数（`content/decor.json`）、色、箱の数。全体図の区画の座標（`src/render/decor.ts` の `CELLS`）。
- **壊すと危ない**:
  - 部品の絵を全体図専用に別途持たない。持つと二重定義に戻る。
  - 全体図の区画の数は、`src/content/schema.ts` の `DECOR_CAPACITY`（壁 5・窓辺 3・床 6・天井 2）と同じ値にそろえる。`contentErrors` は、ある種類の最悪の抽選でも置き場所に収まることを検査しているので、区画を減らすとその検査の前提が崩れる。
  - 箱は部品の枠 `w` × `d` × `h` からはみ出さない（スキーマの検証。`src/content/decor25.test.ts` が、はみ出す箱の部品を通さないことを見ている）。
  - `moving-box`（入居直後の段ボール）は必ず `decor.json` に存在させる（`contentErrors`）。
