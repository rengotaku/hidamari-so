# ADR 0001: 出来事とキャラの種類を content/ の JSON に持ち、zod で検証する

## 背景

元の要望に「ストーリーの保持のしかた、キャラクターの種類などは構造化して保持しなきゃね」と「ストーリーはあればあるだけよい」があった（親 #1 の元要望コメント）。試作（`docs/prototype/hidamari-so.html`）は 1 つの HTML で、日誌の文が処理の中に直接書いてあった（例: 酔った住人の一言の選択肢）。出来事を大量に増やす前に、足し方を決める必要があった（親 #1 Decision Log #5、sub-issue #3）。

## 決定

- 物語のデータはコードに置かず、リポジトリ直下の `content/` に JSON で持つ。
  - `archetypes.json`: キャラの種類
  - `traits.json`: だめな癖
  - `decor.json`: 部屋の装飾の部品
  - `storylets/*.json`: 出来事（1 ファイルに複数件でも 1 件でもよい）
  - `town.json`: 町並みの変化
- `src/content/index.ts` の `parseContent` が、ビルド時に取り込んだ JSON を zod（`src/content/schema.ts`）で検証して `Content` にする。未知のフィールドは拒否する（スキーマは `strictObject` で書いてある）。id の重複、存在しない種類・癖・装飾・出来事の参照（`contentErrors`）も例外にする。検証は起動時とテスト（`make test`）で走るので、書き間違いは CI で落ちる。
- 日誌は組み立て済みの文章でなく、`{t, storyletId, roles, variant}` を保存する。本文は表示のたびに `content` の `texts` から組み立てる（`composeEntry` / `composeParts`）。
- 新規ゲームごとに、初期住人の種類・名前・癖をシードから抽選する。

## 捨てた案

- **出来事をコードに書く**: 試作の形。出来事を足すたびにコードの変更とレビューが要り、「あればあるだけよい」に向かない。
- **日誌を組み立て済みの文字列で保存する**: 保存は簡単だが、後から言い回しを直しても過去の日誌に反映されず、名前を押してプロフィールへ飛ぶ用途（役割の参照）も持てない。保存の版 1 → 2 で、この文字列の日誌を構造に置き換えた（`src/save/migrate.ts` の `v1ToV2`）。
- **検証を実行時の防御に任せる**: 書き間違いが遊んでいる最中にしか分からない。データが増えるほど見つけにくいので、CI で落ちる形にした。

## 変えてよい前提 / 壊すと危ない前提

- **変えてよい**: 出来事・種類・癖・装飾・町並みの変化の中身と件数。`content/` の JSON だけの変更で足せる（コードの変更は要らない）。言い回し（`texts`）の追加・修正も同じ。
- **壊すと危ない**:
  - 保存済みの日誌は「何番目の言い回しか」「`numbers` / `choices` の値」を持つだけなので、`texts` の順番の入れ替え・削除は、過去の日誌が別の言い回しを指す原因になる。出来事の `id` を消す・変えると、その出来事の過去の行は表示されなくなる（`content/README.md` の「日誌との関係」）。
  - スキーマの検証を緩めない。未知のフィールドを通すと、書き間違いが黙って無視される。
  - 保存に入る型（住人の `job` / `traits` など）は `src/save/schema.ts` も検証するので、種類や癖の id を消すと、それを持つ古い保存は読み込みで弾かれる可能性がある（未確認: 実際に弾かれるかどうかは、消した id を持つ保存での読み込みを試していない）。
